How incidents are labeled

Each incident gets exactly one label. The label names the team that would be paged, not what the agent did. Causes go in the involved tags. Decide in this order:

  1. Was there an adversary, or did untrusted input steer the agent? Then it is security. Leaks, exfiltration, supply chain, prompt injection, jailbreaks.
  2. No adversary, but the system did the wrong thing or didn't work? Then it is reliability. Outages, data loss, elevated error rates, wrong output in production.
  3. No adversary, nothing wrong, but worse than it should be? Then it is performance. Latency, saturation, runaway resource or cost consumption.

Where it applies, security entries also carry MITRE ATLAS technique IDs so the same incident can be found in that framework.

Why

AI agents now write code, run shell commands, browse the web, read our inboxes and touch production. They are also easy to trick, confidently wrong, and fast. Very few of the resulting failures get written up in one place. This list exists so that people building and operating agents can learn from each other's incidents instead of repeating them.

"Super intelligent" is tongue in cheek. Most of these incidents did not need super intelligence, just an agent with a tool and no one checking.

Contributing

Know of a public incident caused by an AI agent? Open a pull request against {{ site.repo | remove: "https://" }} and add an entry to _data/incidents.yml. Blog posts, postmortems, news reports, GitHub issues and advisories are all welcome, as long as the source is public and it happened to a real deployment. Researcher proof-of-concepts are out of scope; MITRE ATLAS catalogues those.
